«Постоянные бонусы» в существующем коде означают бонусы между картами одного похода; не следует автоматически превращать их в прогрессию между разными походами. Область сохранения будущих талантов амулета остаётся открытой.

## 2. Границы состояния

| Область | Данные | Срок жизни |
|---|---|---|
| Настройки игрока | Звук, экран и другие пользовательские настройки | Переживают поражение и новый поход |
| Поход | Выбранный герой, его опыт/уровень, текущая карта, прогресс кампании, постоянные бонусы похода | Между картами и перезапусками; сбрасывается при конце похода |
| Карта | Нанятые союзники, расстановка, посещённые узлы/рёбра, обычные усиления карты | В пределах карты; обычный перезапуск не сбрасывает |
| Бой | Текущее HP, цели, снаряды, таймеры и временные эффекты | Только текущий бой |
| Контент | Определения юнитов, формулы, способности, таблицы развития | Не изменяется действиями экземпляров |

Отделить выбранный класс героя от его экземпляра и прогресса. Нельзя при переходе карты пересоздавать героя только по имени и терять D03. Посещения хранить с идентификатором карты, чтобы узел 1 одной карты не конфликтовал с узлом 1 другой.

Принятое восстановление D04 означает: смерть союзника влияет на текущий бой, но сама по себе не удаляет его из состава после победы. Временные боевые эффекты и таймеры не должны случайно переноситься в следующий бой. Политику восстановления активных способностей задать в их определениях.

## 3. Боевая математика

### Подтверждённое направление

Из записей F01–F02: HP, броня, уклонение, урон, скорость атаки, шанс крита, вампиризм, пробивание, скорость движения. Атаки Single/Multi/Heal и ближние/дальние. Порядок: уклонение → броня → крит ×2 → вампиризм. Лечение имеет отдельную проверку крита.

Формула из записей с согласованной границей D05:

```
effectiveArmor = max(0, armor - penetration)
damageAfterArmor = baseDamage / (1 + effectiveArmor / 100)
damageAfterCrit = damageAfterArmor * (critical ? 2 : 1)
actualHpLost = min(targetHpBeforeHit, resolvedDamage)
lifeStealRequested = actualHpLost * lifeStealPercent / 100
```

`resolvedDamage` требует явного правила округления (O01). До его выбора примеры с дробями являются математическими значениями, не утверждёнными целыми потерями HP.

Предложение: HP ограничивать диапазоном от нуля до максимального HP; избыточное лечение отбрасывать. Шансы в контенте — проценты 0…100; некорректные значения отклоняет валидатор. Это защитные правила, подлежащие фиксации при S04.

Скорость атаки в записи: cooldown = 1000 / AS миллисекунд, то есть 1 / AS секунд. В прототипе attackSpeed — задержка в секундах. Предложение: новое поле attacksPerSecond; при миграции старого положительного интервала t использовать AS = 1/t, чтобы не менять исходную частоту атак. Усиления, которые раньше вычитали секунды, требуют отдельного пересчёта, а не смены знака.

### Выбор целей

- Single: ближайший живой противник — из записей.
- Multi: живые противники в радиусе — из записей; независимые проверки по D07.
- Heal: союзник с наибольшей относительной потерей HP — из записей.
- При равенстве приоритетов: предложение использовать устойчивый ID экземпляра для воспроизводимости.
- Самолечение, выбор за пределами радиуса и момент фиксации целей для снаряда требуют спецификации перед S05.

## 5. Прогрессия и получение наград

Герой: четыре класса и десять ступеней по записям, опыт за бои по D02. Предложение: таблица порогов опыта с возрастающими значениями; одна награда может повысить несколько уровней; при максимальном уровне не обращаться к несуществующей следующей ступени.

Открыто до S07: начисление за победу или отдельных врагов; повторные бои; влияние босса; значения порогов; награда выбывшему герою при победе союзников. Эти правила хранить в данных. Не вводить скрытую систему валюты или платного найма до решения экономики.

Союзники: шесть классов и пять ступеней по записям. В прототипе две одинаковые единицы сливаются в следующую ступень, возможен каскад. Сохранение этой механики как общего правила для всех новых классов ещё не подтверждено.

Инженерное требование для S03: результат боя и награда имеют устойчивый ID; повторная загрузка не начисляет повторно юнита, бонус или опыт. Обработка переполненного отряда явная, без молчаливого исчезновения полученной награды; конкретный выбор «замена / резерв / отказ / сначала слияние» открыт.

## 8. Сценарии приёмки согласованных правил

1. Нанять союзников, получить обычный и постоянный бонус, заработать опыт; перейти карту. Герой сохраняет XP/уровень и постоянный бонус, обычный бонус и союзники сброшены. Новый отряд содержит героя.
2. Закрыть игру и продолжить на той же карте. Состав и расстановка сохраняются: перезапуск не равен переходу карты.
3. Проиграть поход, начать новый. Старые XP/уровень героя не переносятся, пользовательские настройки сохранены.
4. Победить с потерями. Перед следующим боем исходный состав восстановлен с полным HP; погибшие союзники не исчезают из состава.
5. Выполнить C03, C05 и C07 с управляемыми бросками; получить согласованные значения.
6. Повторно загрузить экран результата. Опыт и остальные награды не начислены повторно.

## 9. Готовность к следующей работе

Базовые решения S01 согласованы. Спецификация покрывает ближайшее разделение определений/экземпляров S02 и задаёт проверяемые правила похода. Для полного закрытия S01 требуется уточнять открытые решения к соответствующим этапам; вся игровая спецификация не объявляется окончательной.

Следующий технический этап — S02: типы данных и валидатор существующего каталога, изоляция состояния юнита, минимальная тестовая инфраструктура. В нём не требуется автоматически менять боевые формулы, правила наград и игровой контент.

## D08 — полный отряд (согласовано 15.10.2026)

При награде юнитом сначала вычисляется слияние с учётом полученного юнита, включая цепочку слияний. Если после этого в отряде больше шести участников, состав не меняется, а экран показывает нового юнита и предлагает только отказ от награды. Замены союзника, резерва и замены героя нет. При свободном месте сохраняется обычное добавление юнита.

O06 в части политики полного отряда закрыт. Расширение каталога слияний относится к S07.

## S04 — рабочие численные правила (16.10.2026)

Формула, порядок и расхождения источников описаны в GDD_REVIEW_RU.md. O01: выбран floor при применении целого HP, без минимального урона 1; промежуточные множители не округляются. Heal ограничен maxHealth, без воскрешения; вероятности/LS 0–100; AP/броня/урон ≥0. O02 в части единиц: runtime attacksPerSecond, legacy-конфиги переводятся 1/interval; полное поведение таймера/движения остаётся в S05. Это рабочие технические решения реализации, допускающие последующую настройку баланса.
